# T1-29 故障恢复验证

多维度验证沙箱是否从故障中恢复，包括指标、告警、日志、服务健康、接口探活等多个维度，
提供恢复得分和详细的检查报告，为评分体系提供客观依据。

## 背景与目标

### 为什么需要恢复验证？

在故障注入训练中，学员排障后，需要客观地判断系统是否恢复：

1. **客观评分**：不能只靠学员说"我修好了"，需要数据说话
2. **多维度验证**：单一指标恢复不算真正恢复，需要全方位验证
3. **训练闭环**：故障注入 → 学员排障 → **恢复验证** → 评分，形成完整闭环
4. **进度可视化**：学员可以看到自己的恢复进度，知道还差什么
5. **AI 辅助**：AI 可以根据验证结果给出针对性建议

### 恢复验证不是什么

- ❌ 不是简单的"服务能不能访问"
- ❌ 不是单一指标的恢复
- ❌ 不是一次性的检查
- ✅ 是多维度、加权评分的综合验证

## 架构设计

### 分层结构

```
handler (HTTP API, 3个端点)
    ↓
Service (恢复验证服务)
    ├── 检查器注册（5种检查器）
    ├── 并发执行所有检查
    ├── 加权计算得分
    └── 结果缓存
    ↓
5 个检查器：
  ├── MetricsChecker  (指标检查)   → T1-15 metrics.Service
  ├── AlertChecker    (告警检查)   → T1-23 alert.Manager
  ├── LogChecker      (日志检查)   → T1-17 logquery.Service
  ├── HealthChecker   (健康检查)   → T1-20 healthcard
  └── ProbeChecker    (接口探活)   → HTTP 请求
```

### 核心文件

| 文件 | 职责 |
|------|------|
| `internal/recovery/service.go` | 恢复验证服务（核心引擎 + 5 种检查器） |
| `internal/handler/recovery.go` | HTTP 接口（3 个端点） |
| `internal/recovery/service_test.go` | 单元测试 |

## 6 大检查维度

### 1. 指标检查 (Metrics)

检查每个服务的 CPU、内存、错误率是否恢复到正常范围。

| 检查项 | 权重 | 通过条件 |
|--------|------|----------|
| user-service 指标健康 | 10 分 | CPU < 90% && 内存 < 90% && 错误率 < 5% |
| product-service 指标健康 | 10 分 | 同上 |
| order-service 指标健康 | 10 分 | 同上 |

### 2. 告警检查 (Alerts)

检查是否还有活跃的告警。

| 检查项 | 权重 | 通过条件 |
|--------|------|----------|
| 无严重告警 | 20 分 | Critical 级别告警数 = 0 |
| 无警告告警 | 10 分 | Warning 级别告警数 = 0 |

### 3. 日志检查 (Logs)

检查错误日志是否恢复正常。

| 检查项 | 权重 | 通过条件 |
|--------|------|----------|
| 错误日志数量 | 10 分 | 最近 5 分钟错误日志 < 5 条 |

### 4. 健康检查 (Health)

检查所有服务的整体健康状态。

| 检查项 | 权重 | 通过条件 |
|--------|------|----------|
| 所有服务健康 | 15 分 | 所有业务服务健康状态为 healthy |

### 5. 接口探活 (Probe)

检查关键业务接口是否正常响应。

| 检查项 | 权重 | 通过条件 |
|--------|------|----------|
| 用户登录接口 | 5 分 | HTTP 200 |
| 商品列表接口 | 5 分 | HTTP 200 |
| 订单创建接口 | 5 分 | HTTP 200 |

### 权重分布

```
指标检查:   30 分 (30%)
告警检查:   30 分 (30%)
日志检查:   10 分 (10%)
健康检查:   15 分 (15%)
接口探活:   15 分 (15%)
─────────────────────
总计:      100 分
```

**设计考量**：
- 告警和指标各占 30%，是恢复的核心判断依据
- 接口探活占 15%，验证业务功能是否真正可用
- 日志检查占 10%，作为辅助判断

## 验证结果

### 结果结构

```json
{
  "session_id": "sess-abc",
  "sandbox_id": "sandbox-123",
  "overall_status": "failed",
  "score": 65.5,
  "total_checks": 10,
  "passed_count": 7,
  "failed_count": 3,
  "skipped_count": 0,
  "checks": [
    {
      "id": "metrics_user-service_health",
      "name": "user-service 指标健康",
      "category": "metrics",
      "status": "passed",
      "message": "user-service 指标正常",
      "weight": 10,
      "checked_at": 1726000000000
    },
    ...
  ],
  "start_time": 1726000000000,
  "end_time": 1726000002500,
  "duration_ms": 2500
}
```

### 状态定义

| 状态 | 说明 |
|------|------|
| `passed` | 通过（已恢复） |
| `failed` | 未通过（未恢复） |
| `skipped` | 跳过（未启用或不适用） |
| `pending` | 待检查 |

### 得分计算

```
得分 = (通过的权重和 / 总有效权重) × 100
```

- 跳过的检查项不计入总权重
- 得分 100 = 全部通过
- 得分 0 = 全部失败

### 恢复等级

| 得分范围 | 等级 | 说明 |
|----------|------|------|
| 90 ~ 100 | 🟢 完全恢复 | 系统已基本恢复正常 |
| 70 ~ 89 | 🟡 部分恢复 | 主要功能恢复，还有些小问题 |
| 50 ~ 69 | 🟠 初步恢复 | 核心问题解决了，但还有较多问题 |
| 0 ~ 49 | 🔴 未恢复 | 系统仍处于故障状态 |

## HTTP API

### 3 个端点

| 方法 | 路径 | 说明 |
|------|------|------|
| POST | `/api/v1/recovery/verify` | 执行一次恢复验证 |
| GET | `/api/v1/recovery/result` | 获取最近一次验证结果 |
| GET | `/api/v1/recovery/checks` | 列出所有检查项配置 |

### 验证流程

```
学员点击"验证恢复"
    ↓
前端调用 POST /api/v1/recovery/verify
    ↓
后端并发执行 5 类检查
    ├── 指标检查（3个服务）
    ├── 告警检查（2项）
    ├── 日志检查（1项）
    ├── 健康检查（1项）
    └── 接口探活（3个接口）
    ↓
计算加权得分
    ↓
返回验证结果（得分 + 每项详情）
    ↓
前端展示：
  - 总体得分和等级
  - 各检查项通过/失败状态
  - 失败项的具体原因
```

## 性能考量

### 单次验证耗时

| 检查类型 | 耗时 | 说明 |
|----------|------|------|
| 指标检查 | ~200ms | 每个服务一次 Prometheus 查询 |
| 告警检查 | ~50ms | 内存查询 |
| 日志检查 | ~100ms | Loki 计数查询 |
| 健康检查 | ~100ms | 复用指标数据 |
| 接口探活 | ~500ms | 3 个 HTTP 请求 |
| **总计** | **~1s** | 并发执行，取最长的那个 |

### 频率限制

- 建议学员手动触发，不自动轮询
- 可以加限流：每 30 秒最多验证一次
- 避免频繁验证给 Prometheus/Loki 造成压力

## 设计要点

1. **多维度验证**：5 大类 10 项检查，全方位判断恢复
2. **加权评分**：不同检查项权重不同，重要的占比高
3. **并发执行**：所有检查器并发执行，总耗时 ≈ 最慢的那个
4. **可扩展**：Checker 接口化，新增检查类型只需注册新的 Checker
5. **结果缓存**：保存最近一次结果，前端可以随时查看
6. **容错设计**：单个检查器失败不影响整体，标记为失败即可
7. **详细反馈**：每项都有 message，告诉学员具体哪里没恢复
8. **可配置**：检查项可以启用/禁用，权重可以调整

## 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 验证耗时太长 | 体验差 | 并发执行 + 超时控制 |
| 检查项不准 | 误判恢复 | 持续优化阈值和权重 |
| 探活不稳定 | 网络波动导致误判 | 重试机制 + 合理超时 |
| 学员频繁点击 | 后端压力大 | 限流 + 结果缓存 |
| 权重不合理 | 评分不公平 | 根据训练数据持续调优 |

## 后续优化方向

1. **历史趋势**：展示多次验证的得分变化曲线
2. **恢复建议**：根据失败项自动给出恢复建议（AI 辅助）
3. **自定义检查项**：不同故障场景可以配置不同的检查项
4. **灰度验证**：先验证核心功能，再验证边缘功能
5. **持续验证**：训练结束前持续验证，确保稳定恢复
6. **对比基线**：和故障注入前的基线数据对比
7. **资源检查**：增加资源使用量的检查（CPU/内存使用是否合理）
8. **业务指标验证**：验证业务指标（如下单成功率、用户注册数）是否恢复
