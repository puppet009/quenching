# T1-20 服务健康卡片

整合指标数据（T1-15）和告警数据（T1-23），提供服务健康卡片视图，
支持 RESTful API 和 WebSocket 实时推送，为训练界面的健康监控面板提供数据。

## 背景与目标

### 为什么需要健康卡片？

训练界面需要一个直观的健康监控面板，让学员：
1. **一眼看清**：哪些服务正常，哪些有问题
2. **快速定位**：点击异常服务查看详情
3. **实时感知**：状态变化及时推送
4. **告警关联**：看到告警数量和严重程度

如果让前端直接调指标 API + 告警 API：
- 前端要合并数据，逻辑复杂
- 多次 HTTP 请求，性能差
- 状态判定逻辑重复（前端后端各写一遍）
- 实时推送难做

T1-20 提供统一的健康卡片服务，整合指标和告警，提供清晰的健康状态。

## 架构设计

### 分层结构

```
handler (HTTP API, 4个端点)
    ↓
Service (健康卡片服务层)
    ├── 指标数据聚合（MetricsProvider）
    ├── 告警数据聚合（AlertProvider）
    ├── 状态判定引擎
    ├── 缓存层（10s TTL）
    └── 定时推送（EventPublisher）
    ↓
metrics.Service (T1-15) + alert.Manager (T1-23)
    ↓
eventbus.Publisher (T1-19)
    ↓
WS Gateway → 前端
```

### 核心文件

| 文件 | 职责 |
|------|------|
| `internal/healthcard/service.go` | 健康卡片服务（核心逻辑） |
| `internal/handler/healthcard.go` | HTTP 接口（4 个端点） |
| `internal/healthcard/service_test.go` | 单元测试 |

## 健康状态定义

### 4 种状态

| 状态 | 颜色 | 说明 | 判定条件 |
|------|------|------|----------|
| `healthy` | 🟢 绿色 | 健康 | 指标正常 + 无告警 |
| `warning` | 🟡 黄色 | 警告 | 指标正常 + 有 warning 告警 |
| `critical` | 🔴 红色 | 严重 | 指标异常 **或** 有 critical 告警 |
| `unknown` | ⚪ 灰色 | 未知 | 数据获取失败 |

### 判定优先级

```
critical 告警? ──是──→ critical
    ↓ 否
指标不健康? ──是──→ critical
    ↓ 否
warning 告警? ──是──→ warning
    ↓ 否
healthy
```

**为什么 critical 告警比指标异常优先？**
- 告警是已经确认的问题，严重性更高
- 指标异常可能是瞬时的，告警是持续满足条件的

## HTTP API

### 4 个端点

| 方法 | 路径 | 说明 | 使用场景 |
|------|------|------|----------|
| GET | `/api/v1/health/overview` | 健康概览（所有服务卡片） | 健康面板主页面 |
| GET | `/api/v1/health/service/:service` | 单个服务详情 | 点击服务卡片 |
| GET | `/api/v1/health/summary` | 精简摘要 | 顶部状态栏/小程序 |

## 实时推送

### 推送机制

通过 T1-19 事件总线推送，事件类型：`health_status`

**推送频道**：`sandbox:{sandbox_id}`

**推送频率**：可配置，默认 30 秒一次

**推送内容**：完整的 DashboardOverview

### 为什么是定时推送而不是事件驱动？

| 方案 | 优点 | 缺点 |
|------|------|------|
| **定时推送**（当前） | 实现简单、流量可控、前端好处理 | 有延迟（最多 30s） |
| 事件驱动 | 实时性好 | 实现复杂、可能推送太频繁 |

**设计决策**：
- 健康面板不需要毫秒级实时，30 秒延迟完全可接受
- 定时推送流量可控，不会因为告警风暴导致前端卡死
- 后续可以优化为"状态变化时才推送"，减少无效推送

### 前端使用方式

```javascript
// 1. 连接 WebSocket 时订阅沙箱频道
// 2. 监听 health_status 事件
ws.on('health_status', (data) => {
  updateHealthDashboard(data);  // 更新整个健康面板
});

// 3. 首次加载调一次 overview API
fetch('/api/v1/health/overview?sandbox_id=xxx')
```

## 缓存策略

### 为什么需要缓存？

- 健康面板是高频访问的页面
- 每次都查 Prometheus + 告警引擎，压力大
- 指标数据 30 秒内变化不大，缓存完全够用

### 缓存设计

```
请求 → 检查缓存 → 未过期 → 返回缓存
              → 已过期 → 重新计算 → 更新缓存 → 返回
```

- **TTL**：10 秒
- **存储**：内存（单实例）
- **粒度**：按 sandbox_id 缓存
- **刷新**：POST /refresh 接口强制刷新

### 缓存 vs 实时推送

- **HTTP API**：走缓存（10s TTL），适合页面加载和手动刷新
- **WebSocket 推送**：每次推送都强制刷新，保证实时性

## 性能考量

### 单次概览查询

- 3 个服务，每个服务 2 次指标查询（健康检查 + 全量快照）
- 1 次告警查询（按服务统计）
- 并发查询，总耗时 ≈ 最慢的那次查询

预估：200ms ~ 500ms

### 缓存命中

直接返回内存数据，< 1ms

### 实时推送

- 30 秒一次，每次约 2KB 数据
- 100 个在线用户 ≈ 200KB/s 带宽
- 完全可控

## 与上下游的关系

### 上游依赖
- **T1-15 核心指标 API**：指标数据源（健康检查 + 指标快照）
- **T1-23 告警规则引擎**：告警数据源（按服务统计告警数）
- **T1-19 事件订阅分发**：实时推送通道

### 下游使用
- **T2-19 实时图表**：健康状态作为图表的上下文信息
- **T2-22 故障注入日志观察**：从健康卡片跳转到日志
- **T2-15 恢复判定**：健康状态是恢复判定的重要依据
- 训练界面主面板：健康状态概览展示

## 设计要点

1. **数据整合**：一个接口返回所有健康数据，前端不用多次请求
2. **状态分级**：4 级健康状态，直观易懂
3. **按严重排序**：critical 在前，学员最先看到问题最严重的
4. **缓存优化**：10s TTL，减轻 Prometheus 和告警引擎压力
5. **实时推送**：通过 eventbus 定时推送，前端无需轮询
6. **接口化设计**：MetricsProvider/AlertProvider 都是接口，方便测试和替换
7. **并发查询**：多个服务的指标并发查，减少总耗时
8. **容错设计**：单个服务数据失败不影响整体，标记为 unknown

### 交互流程

1. 页面加载 → 调用 overview 接口 → 渲染卡片
2. WebSocket 收到 health_status 事件 → 更新卡片数据
3. 点击某个服务卡片 → 跳转到服务详情页（T2-19 图表 + T2-22 日志）
4. 点击刷新按钮 → 调用 refresh 接口 → 立即更新

## 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 指标查询慢 | 健康面板加载慢 | 缓存 + 并发查询 |
| 告警数据不准 | 状态判定错误 | 告警引擎持续优化阈值 |
| 推送延迟 | 状态变化不及时 | 30s 可接受，重要告警单独推 |
| 沙箱服务数量变化 | 卡片数量不对 | 动态服务发现（后续优化） |

## 后续优化方向

1. **动态服务发现**：从 Prometheus 自动发现服务列表，不用硬编码
2. **状态变化推送**：只有状态变化时才推送，减少无效推送
3. **健康趋势**：展示过去 1 小时的健康状态变化曲线
4. **服务依赖图**：展示服务间调用关系，直观看到故障影响范围
5. **根因分析**：基于告警和指标关联，自动分析可能的根因
6. **历史记录**：健康状态历史记录，支持回溯查看
7. **自定义卡片**：用户可以自定义卡片显示的指标
8. **多沙箱对比**：管理后台对比多个沙箱的健康状态
