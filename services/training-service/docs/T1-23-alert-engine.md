# T1-23 告警规则引擎

告警规则引擎，支持阈值型、趋势型、日志关键词型三种规则，
提供完整的告警状态机、去重抑制、事件推送和管理 API。

## 背景与目标

### 为什么需要告警规则引擎？

在故障注入训练平台中，告警有多重作用：
1. **学员感知**：告警实时推送到训练界面，让学员感知到问题
2. **排障提示**：告警信息帮助学员定位故障方向
3. **恢复判定**：告警恢复是训练成功的重要标志
4. **运营监控**：管理后台可以查看所有沙箱的告警情况

如果每个模块自己实现告警逻辑：
1. 告警口径不一致（有的用瞬时值，有的用平均值）
2. 状态管理混乱（触发/恢复/确认各写各的）
3. 告警风暴（没有去重和抑制，告警刷屏）
4. 难以扩展（新增告警类型改动大）

T1-23 提供统一的告警规则引擎，解决这些问题。

## 三种告警规则

### 1. 阈值型 (threshold)

**原理**：指标当前值与阈值比较，满足条件触发。

**适用场景**：
- CPU 使用率 > 90%
- 错误率 > 5%
- 内存使用率 > 85%
- QPS < 10（服务可能挂了）

**参数**：
- `metric`：指标名
- `operator`：比较操作符（>/</>=/<=/==/!=）
- `threshold`：阈值

### 2. 趋势型 (trend)

**原理**：比较时间窗口内前半段和后半段的平均值，计算变化百分比。

**适用场景**：
- 内存持续上升（可能内存泄漏）
- QPS 持续下降（可能服务异常）
- 错误率持续上升（问题在恶化）

**参数**：
- `metric`：指标名
- `trend_direction`：趋势方向（up/down）
- `trend_change_pct`：变化百分比阈值
- `trend_duration`：观察时间窗口

### 3. 日志关键词型 (log_keyword)

**原理**：统计指定时间窗口内日志中关键词出现的次数。

**适用场景**：
- 出现 OutOfMemoryError
- 出现 NullPointerException
- 出现数据库连接失败
- 出现特定错误码

**参数**：
- `log_keyword`：关键词（大小写不敏感）
- `log_level`：日志级别过滤（可选）
- 评估窗口：默认 1 分钟
- 触发阈值：默认出现 1 次即触发

## 告警状态机

### 5 种状态

| 状态 | 说明 |
|------|------|
| `ok` | 正常，未触发 |
| `pending` | 首次触发，等待持续时间验证（防抖动） |
| `firing` | 告警中，已满足持续时间 |
| `acknowledged` | 已确认（有人点了确认） |
| `resolved` | 已恢复 |

### 状态转移图

```
           触发              持续时间满足
  OK ─────────→ Pending ────────────────→ Firing
  ↑                │                        │  │
  │                │ 恢复                   │  │
  │                ↓                        │  │
  └────────────────┘                        │  │
                                            │  │
                      恢复                   │  │
  Resolved ←────────────────────────────────┘  │
     ↑                                         │
     │              确认                        │
     └──────────── Acknowledged ←──────────────┘
```

### 防抖动机制 (ForDuration)

告警不是一触发就通知，而是需要持续满足条件一段时间：

```
指标值
  ↑
阈值 ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
  │      ╱╲        ╱╲
  │     ╱  ╲      ╱  ╲        ╱╲
  │────╱────╲────╱────╲──────╱──╲──→ 时间
  │   ╱      ╲  ╱      ╲    ╱    ╲
  │  ╱        ╲╱        ╲  ╱      ╲
  │ ╱                    ╲╱        ╲╶╶╶╶╶
  │
       │      │  │      │  │        │
       抖动   恢  抖动   恢  持续     触发告警
              复          复  满足
```

**为什么需要？**
- 防止瞬时尖峰误报
- 减少告警骚扰
- 只有真正持续的问题才通知

### 重复告警 (RepeatInterval)

告警持续期间，每隔一段时间重复通知一次：

- `RepeatInterval = 0`：只通知一次（触发时）
- `RepeatInterval = 5m`：每 5 分钟重复通知一次
- 防止告警被遗忘

## 告警级别

| 级别 | 说明 | 示例 |
|------|------|------|
| `info` | 提示性告警 | QPS 略有下降 |
| `warning` | 警告，需要关注 | CPU > 80% |
| `critical` | 严重，需要立即处理 | CPU > 95% 或 服务不可用 |

## 去重与抑制

### 去重

同一条规则 + 同一个沙箱 + 同一个服务 → 同一个告警实例

```
alertID = sha1(ruleID + sandboxID + service)[:8]
```

同一时间只有一个活跃告警实例，不会重复创建。

### 抑制

1. **持续时间抑制**：短暂波动不触发
2. **重复间隔**：告警中不会每分钟都通知
3. **确认机制**：确认后告警仍在，但不再重复通知
4. **自动恢复**：指标正常后自动转 resolved

## 标准告警事件

通过 T1-19 事件总线推送，事件类型为 `alert`：

```json
{
  "type": "alert",
  "ts": 1726000000000,
  "data": {
    "alert_id": "a1b2c3d4e5f6",
    "sandbox_id": "sandbox-123",
    "rule_id": "rule-cpu-high",
    "rule_name": "CPU 使用率过高",
    "severity": "critical",
    "metric": "cpu_usage",
    "value": 95.5,
    "threshold": 90.0,
    "message": "CPU 使用率过高 (user-service) 当前值 95.50% 大于阈值 90.00%",
    "timestamp": 1726000000000
  }
}
```

**推送频道**：`sandbox:{sandbox_id}`

恢复时也推送同样格式的事件，message 表示已恢复。

## 内置默认规则

每个沙箱启动时，自动注册以下默认规则：

| 规则名 | 类型 | 指标 | 条件 | 级别 |
|--------|------|------|------|------|
| CPU 使用率过高 | 阈值 | cpu_usage | > 90% | critical |
| 内存使用率过高 | 阈值 | memory_usage | > 90% | critical |
| 错误率过高 | 阈值 | error_rate | > 5% | warning |
| 服务不可用 | 阈值 | qps | < 1 | critical |
| 内存持续上升 | 趋势 | memory_usage | 5分钟上升 20% | warning |
| OOM 异常 | 日志关键词 | - | OutOfMemoryError | critical |
| NPE 异常 | 日志关键词 | - | NullPointerException | warning |

**设计考虑**：
- 覆盖系统和业务的关键指标
- 级别区分明确（critical 立即处理，warning 关注即可）
- 可以通过 API 动态调整

## 设计要点

1. **三种规则类型**：覆盖阈值、趋势、日志关键词三大场景
2. **状态机驱动**：5 种状态 + 清晰的转移规则，行为可预测
3. **防抖动**：ForDuration 机制，避免瞬时尖峰误报
4. **去重设计**：同规则同目标只有一个告警实例
5. **接口化设计**：MetricsSource/LogSource/Publisher 都是接口，方便 mock
6. **事件驱动**：告警状态变化通过事件总线推送，解耦前端
7. **定时评估**：默认 30 秒一次，可配置
8. **自动清理**：已恢复告警 24 小时后自动清理

## 性能考量

### 评估性能

- 单条阈值型规则评估：< 10ms（一次 Prometheus 查询）
- 单条趋势型规则评估：< 50ms（区间查询 + 计算）
- 单条日志关键词型：< 100ms（Loki 计数查询）

### 容量估算

每沙箱默认 7 条规则，30 秒评估一次：
- 每秒查询次数：7 / 30 ≈ 0.23 次/沙箱
- 100 个沙箱：23 次/秒
- Prometheus/Loki 完全扛得住

### 优化方向

1. **并发评估**：多个规则并发查询，减少总耗时
2. **数据缓存**：同一指标的查询结果短时间缓存
3. **规则分组**：相同指标的规则合并查询
4. **降级策略**：Loki/Prometheus 不可用时跳过评估

## 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 告警风暴 | 前端告警刷屏 | 去重 + 抑制 + 分级 |
| 误报率高 | 学员不信任告警 | 持续时间 + 合理阈值 |
| 漏报 | 问题没被发现 | 多种规则类型互补 + 默认规则 |
| 数据源不可用 | 告警评估失败 | 静默失败 + 不影响其他规则 |

## 后续优化方向

1. **告警聚合**：相似告警自动聚合（如同一服务多个指标告警）
2. **告警抑制规则**：高级别告警抑制低级别（如 critical 抑制 warning）
3. **告警升级**：长时间未处理的告警自动升级
4. **告警通知渠道**：支持邮件/钉钉/企业微信通知
5. **告警模板**：预置常用规则模板，一键导入
6. **告警历史**：告警记录落库，支持历史查询和分析
7. **智能阈值**：基于历史数据动态调整阈值
8. **告警关联**：根因分析，关联多个告警找出根因
