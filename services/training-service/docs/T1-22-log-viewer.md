# T1-22 故障注入日志观察

在 T1-17 日志查询 API 的基础上，提供训练场景下的日志观察功能，
包括关键词高亮、日志上下文、实时日志流、日志统计和导出。

## 背景与目标

### 为什么需要日志观察？

故障注入训练中，日志是学员排障的最重要信息来源：
1. **快速定位**：通过错误日志快速找到故障点
2. **分析根因**：查看日志上下文，理解故障发生的前后逻辑
3. **实时监控**：观察操作后日志的变化，验证修复效果
4. **复盘分析**：导出日志用于训练后的复盘

T1-17 提供了基础的日志查询能力，但缺少训练场景特有的功能：
- 错误关键词高亮（学员一眼看到问题）
- 日志上下文（点击查看前后 N 条）
- 实时日志流（像 tail -f 一样实时滚动）
- 日志统计（错误数、警告数一目了然）
- 日志导出（方便离线分析）

T1-22 就是在 T1-17 之上，提供这些训练场景的增强功能。

## 架构设计

### 分层结构

```
handler (HTTP API, 6个端点)
    ↓
Service (日志观察服务层)
    ├── 查询 + 高亮处理
    ├── 日志上下文
    ├── 日志统计（并发查4个指标）
    ├── 日志导出
    └── 实时日志流（StreamManager）
    ↓
LogProvider (T1-17 logquery.Service)
    ↓
Loki (沙箱日志存储)
    ↓
eventbus.Publisher (T1-19) → WS Gateway → 前端
```

### 核心文件

| 文件 | 职责 |
|------|------|
| `internal/logviewer/service.go` | 日志观察服务（核心逻辑） |
| `internal/handler/logviewer.go` | HTTP 接口（6 个端点） |
| `internal/logviewer/service_test.go` | 单元测试 |

## 6 大功能

### 1. 日志查询（带高亮）

基于 T1-17 的查询能力，增加关键词高亮：

**高亮类型**：
- 🔴 **error**：ERROR、Exception、OutOfMemoryError、5xx 等
- 🟡 **warn**：WARN、Warning、timeout、retry 等
- 🔵 **keyword**：自定义关键词（用户搜索的词）

**高亮数据结构**：
```json
{
  "hl": [
    {"s": 20, "e": 25, "t": "error"},
    {"s": 45, "e": 52, "t": "warn"}
  ]
}
```

`s` = 起始位置，`e` = 结束位置，`t` = 类型

前端根据这些区间给文字上色。

### 2. 日志上下文

点击某条日志，查看前后各 N 条上下文：

```
...（之前的 10 条）...
────────── 选中的日志 ──────────
...（之后的 10 条）...
```

**使用场景**：
- 错误日志出现了，想看看之前发生了什么
- 想了解错误发生后的连锁反应
- 查看完整的请求链路日志

### 3. 实时日志流

像 `tail -f` 一样实时滚动日志：

- 基于 T1-17 的 tail 接口
- 定时轮询（默认 3 秒），只拉取新日志
- 通过 T1-19 eventbus 推送到前端
- 前端 WebSocket 收到后追加到列表底部

**推送事件格式**：
```json
{
  "type": "log_lines",
  "ts": 1726000000000,
  "data": {
    "sandbox_id": "sandbox-123",
    "service": "order-service",
    "count": 5,
    "lines": [ /* LogLine 数组 */ ]
  }
}
```

### 4. 日志统计

统计指定时间范围内的日志概况：

```json
{
  "total_count": 15420,
  "error_count": 156,
  "warn_count": 342,
  "info_count": 14922,
  "by_service": {
    "order-service": 8200,
    "user-service": 4520,
    "product-service": 2700
  },
  "time_range": "10:00:00 ~ 11:00:00"
}
```

**用途**：
- 日志概览卡片
- 错误趋势判断
- 快速定位哪个服务问题最多

### 5. 日志导出

导出指定时间范围的日志为纯文本文件：

- 支持按服务、级别、关键词过滤
- 最多导出 5000 条（防止导出过大）
- 文件名格式：`logs_{sandbox_id}_{时间}.log`
- 每行格式：`时间 [服务] [级别] 内容`

**使用场景**：
- 训练复盘时导出日志分析
- 把日志发给 AI 分析
- 离线保存问题现场

### 6. 服务/级别过滤

所有查询接口都支持：
- 按服务过滤（user-service / product-service / order-service）
- 按级别过滤（DEBUG / INFO / WARN / ERROR / FATAL）
- 按关键词搜索（大小写不敏感）

## HTTP API

### 6 个端点

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/v1/logviewer/query` | 日志查询（带高亮） |
| GET | `/api/v1/logviewer/context` | 日志上下文 |
| GET | `/api/v1/logviewer/stats` | 日志统计 |
| GET | `/api/v1/logviewer/export` | 日志导出（文件下载） |
| POST | `/api/v1/logviewer/stream/start` | 启动实时日志流 |
| POST | `/api/v1/logviewer/stream/stop` | 停止实时日志流 |

### 查询接口参数

| 参数 | 必填 | 默认值 | 说明 |
|------|------|--------|------|
| sandbox_id | ✅ | - | 沙箱ID |
| service | ❌ | 全部 | 服务名 |
| level | ❌ | 全部 | 日志级别 |
| keyword | ❌ | - | 关键词 |
| start_time | ❌ | 1小时前 | 开始时间（毫秒） |
| end_time | ❌ | 当前 | 结束时间（毫秒） |
| limit | ❌ | 200 | 返回条数 |
| direction | ❌ | backward | 方向：backward(从新到旧) / forward |

## 与上下游的关系

### 上游依赖
- **T1-17 日志查询 API**：日志数据源（查询/统计/tail）
- **T1-19 事件订阅分发**：实时日志推送通道
- **T1-16 日志采集到 Loki**：日志存储后端

### 下游使用
- **T2-22 故障注入日志观察前端**：日志面板 UI
- **T2-15 恢复判定**：日志中出现特定信息作为恢复依据
- **T4-11 沙箱监控后端**：管理后台查看日志
- **T5-4 训练复盘报告**：日志数据用于生成复盘报告

### 数据流向

```
Promtail → Loki → logquery.Service → logviewer.Service → HTTP API
                                              ↓
                                        eventbus → WS Gateway → 前端
```

## 性能考量

### 查询性能

- 单次查询走 Loki，延迟约 100~500ms
- 高亮处理在内存中完成，几乎无额外开销
- 200 条日志高亮处理 < 5ms

### 实时推送性能

- 默认 3 秒一次推送
- 每次最多推送 100 条新日志
- 100 条日志约 20KB，带宽压力小
- 没有新日志时不推送，节省流量

### 导出性能

- 最多 5000 条，约 500KB~1MB
- 组装纯文本 < 10ms
- 直接返回 text/plain，浏览器自动下载

## 设计要点

1. **关键词高亮**：错误/警告/自定义三级高亮，前端直观展示
2. **日志上下文**：30 分钟时间窗口，前后各 N 条，快速定位问题
3. **实时日志流**：定时轮询 + 增量推送，像 tail -f 一样流畅
4. **并发统计**：4 个计数并发查，减少总耗时
5. **导出友好**：纯文本格式，兼容各种日志分析工具
6. **接口化设计**：LogProvider 是接口，方便 mock 和测试
7. **流管理器**：每个沙箱独立 tail goroutine，互不干扰
8. **错误行标记**：IsError 字段，前端可以快速筛选错误行

## 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 日志量太大 | 查询慢、前端渲染卡 | limit 限制 + 分页 + 虚拟滚动 |
| 实时推送延迟 | 日志不实时 | 3 秒可接受，可配置更短 |
| 关键词高亮不准 | 误标/漏标 | 可配置关键词列表，持续优化 |
| 导出文件太大 | 下载慢、内存高 | 5000 条上限 + 提示缩小时间范围 |

## 后续优化方向

1. **日志高亮主题**：支持深色/浅色主题，自定义高亮颜色
2. **日志折叠**：相同类型的错误日志可以折叠，减少干扰
3. **日志跳转**：点击日志中的 traceId 跳转到关联日志
4. **日志收藏**：收藏重要日志，用于训练复盘
5. **日志标注**：在日志上加标注和评论，协作排障
6. **智能过滤**：AI 自动识别重要日志，过滤掉噪音
7. **日志对比**：对比故障前后的日志差异
8. **实时告警**：实时日志流中出现特定关键词立即告警
