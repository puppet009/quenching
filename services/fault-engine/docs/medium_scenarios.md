|---|------|------|------|------|----------|------|

## 各剧本详细说明

### 剧本#3：订单慢查询致延迟

**根因**：订单服务数据库查询未加索引，大表扫描导致接口延迟飙升。

**故障模拟方式**：给 order-svc Pod 的网络加 300ms 延迟，模拟慢查询导致的接口响应慢。

**传导路径**：
1. 订单查询接口变慢 → P99 飙升
2. 下单流程依赖查单 → 下单接口也变慢
3. 延迟过高触发超时 → 错误率上升

**恢复判定阈值**：
- order-svc P99 延迟 ≤ 200ms
- order-svc 错误率 ≤ 1%

**正确修复路径**：
1. 查看监控发现 order-svc P99 飙升
2. 查日志发现慢查询 SQL
3. 添加索引 / 优化 SQL
4. 接口延迟恢复正常

### 剧本#4：商品服务网络丢包致级联超时

**根因**：商品服务网络丢包率高，订单服务调用商品服务时频繁超时。

**故障模拟方式**：给 product-svc Pod 注入 30% 网络丢包。

**传导路径**（级联效应）：
1. product-svc 网络丢包 → 对外接口响应不稳定
2. order-svc 调用 product-svc（扣库存、查商品）→ 频繁超时
3. order-svc 下单失败率飙升 → 用户侧体验差

**触发方式**：metric 触发 —— 当 order-svc QPS > 20 时才注入（模拟有流量时才暴露问题）。

**恢复判定阈值**：
- order-svc 错误率 ≤ 1%
- order-svc P99 延迟 ≤ 300ms

**正确修复路径**：
1. 监控看到 order-svc 错误率飙升
2. 查日志发现调用 product-svc 超时
3. 排查 product-svc 网络状况
4. 修复网络问题 → 级联恢复

### 剧本#5：用户服务内存泄漏

**根因**：用户服务缓存未设置过期策略，内存持续增长，最终 OOM。

**故障模拟方式**：给 user-svc Pod 注入 85% 内存占用（模拟泄漏到高水位）。

**传导路径**：
1. 内存持续上涨 → GC 频率增加
2. GC 占用 CPU → 接口响应变慢
3. 内存超过限制 → Pod OOM → 服务不可用

**恢复判定阈值**：
- user-svc 内存使用率 ≤ 70%

**正确修复路径**：
1. 监控发现 user-svc 内存持续上涨
2. heap dump 分析泄漏点
3. 修复代码（加过期策略 / 释放资源）
4. 内存使用率稳定在正常水平

## 校准说明

阈值为初始估算值，实际联调时需根据真实环境指标校准：
- 正常基线需要在无故障稳态流量下采集
- 恢复阈值应略高于基线（给波动留余量）
- 稳定窗口默认 30s，可按实际调整

## 与简单剧本的对比

| 维度 | 简单（T2-25） | 中等（T2-26） |

| 故障类型 | CPU满载、磁盘打满（直接可见） | 慢查询、网络丢包、内存泄漏（需要排查） |

| 预计修复时间 | 短 | 中（15-25分钟） |
