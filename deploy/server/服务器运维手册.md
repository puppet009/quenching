# 淬火平台 · 服务器运维命令手册

适用：单机 k3s 部署（火山引擎）。本手册面向**日常更新与排障**，首次完整部署见 `deploy/server/README.md`。

---

## 0. 环境速览

| 项目 | 值 |
| --- | --- |
| 仓库目录 | `/data/src/quenching` |
| 命名空间 | `platform`（硬约束，不可改名） |
| 镜像仓库 | 本机 containerd，无需远程仓库 |
| 镜像 Tag | 当前候选 `0.1.0-alpha.1`，每个发布版本使用独立标签 |
| 用户端 web | `http://<公网IP>:30080` |
| 管理端 admin | `http://<公网IP>:30081` |
| API 网关 | `http://<公网IP>:30082` |

### 工作负载名称（Deployment）

> 名称**不带** `quenching-` 前缀。`quenching` 是 Helm release 名，不是资源名。

| 类别 | 名称 |
| --- | --- |
| 后端服务 | `api-gateway`、`content-service`、`user-service`、`training-service`、`review-service`、`fault-engine`、`sandbox-service`、`ai-service` |
| 前端 | `web`、`admin` |

中间件（非本 Chart 的 Deployment）：`postgresql`（StatefulSet）、`rabbitmq`、`prometheus-server`。

## 1. 每次登录先做：导出 kubeconfig

k3s 自带的 `kubectl` 会自动读 `/etc/rancher/k3s/k3s.yaml`，但标准 `helm` 只认 `KUBECONFIG` 或 `~/.kube/config`。若不设置，helm 会退回连接 `localhost:8080` 并报 `connection refused`。

```bash
# 临时生效（仅当前终端）
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl get nodes      # 能列出节点即正常
```

一劳永逸（复制成 helm 默认会读的位置，之后所有新终端免设置）：

```bash
mkdir -p /root/.kube
cp /etc/rancher/k3s/k3s.yaml /root/.kube/config
chmod 600 /root/.kube/config
```

## 2. 代码更新标准流程

先拉取代码：

```bash
cd /data/src/quenching
git pull
```

之后**按改动类型**选择下面的操作（可组合）：

| 改动内容 | 需要做的操作 |
| --- | --- |
| Go 服务业务代码 | 重建该服务镜像 + 重启该服务（见 §3） |
| `templates/` 模板文件 | 重建相关服务镜像（模板被 COPY 进镜像）+ 重启（见 §3） |
| 数据库迁移 `migrations/` | 重建镜像（迁移文件在镜像内）+ 跑迁移（见 §4） |
| Helm 模板 / values（如 `deploy/helm/**`） | `helm upgrade`（见 §5），通常自动滚动重启 |
| 前端 `apps/web`、`apps/admin` | 重建前端镜像 + 重启（见 §3） |

> 发布时使用新标签，构建完成后更新 Helm 与 web/admin 的镜像引用，不能只 `rollout restart` 旧标签。若仅在隔离开发环境中重建同一开发标签，需要显式传入当前 `IMAGE_TAG`，并重启对应服务。已发布的标签保持不变；跨版本完整步骤见 [版本与发布](../../docs/releases.md)。

## 3. 构建镜像并重启服务

### 3.1 构建镜像

`images.sh` 会用 Docker 构建并自动 `docker save | k3s ctr images import` 导入 k3s containerd。

```bash
cd /data/src/quenching/deploy/server

bash images.sh                      # 构建全部 11 个镜像
bash images.sh content-service      # 只构建一个（最常用）
bash images.sh web admin            # 同时构建多个
NOCACHE=1 bash images.sh <名称>     # 不用缓存重建
```

可选目标名：`api-gateway` `content-service` `user-service` `training-service` `review-service` `fault-engine` `sandbox-service` `ai-service` `web` `admin` `log-agent`。

### 3.2 重启对应服务，让新镜像生效

```bash
kubectl -n platform rollout restart deploy/content-service
kubectl -n platform rollout status  deploy/content-service     # 等待滚动更新完成
```

前端同理：

```bash
kubectl -n platform rollout restart deploy/web
kubectl -n platform rollout status  deploy/web
```

> Pod 重启后若出现 `ImagePullBackOff`，说明镜像没导入成功，重跑 `images.sh` 的导入段或检查 `k3s ctr images ls | grep quenching`。

## 4. 数据库迁移

迁移文件来自**服务镜像内** `/app/migrations`，因此**必须先重建好对应服务的新镜像**，再跑迁移。

```bash
cd /data/src/quenching/deploy/server

bash migrate.sh clean      # 已有旧 Job 时先删除；仅删除迁移 Job，不删除数据
bash migrate.sh            # 生成六个服务的迁移 Job 并等待全部完成
bash migrate.sh render     # 只打印 YAML，不执行
bash migrate.sh clean      # 删除旧迁移 Job（失败后重跑前用）
```

迁移以 Job 形式运行，命名为 `migrate-<服务名>`（如 `migrate-training-service`），六服务共库、各自独立迁移表（`schema_migrations_<服务名>`）。

查看某个失败的迁移日志：

```bash
kubectl -n platform logs job/migrate-training-service -c migrate
```

## 5. Helm 配置更新（路由 / values / 编排变更）

当改动涉及 `deploy/helm/`（例如网关路由表 `_helpers.tpl`、Deployment 编排、配置项）时执行。

```bash
cd /data/src/quenching
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml

helm upgrade quenching ./deploy/helm -n platform --reuse-values
```

- `--reuse-values`：原样复用首次部署的全部配置，**包括真实的 JWT_SECRET / INTERNAL_TOKEN**，不换密钥、不掉线。
- **不要再加 `-f deploy/server/values-server.yaml`**：该文件里密钥是占位符，命令行 `-f` 的优先级高于 `--reuse-values`，可能用占位符覆盖真实密钥导致全员登录失效。
- Pod 模板（含 env）发生变化时会自动滚动重启，无需手动 restart。

查看 release 当前状态与历史版本：

```bash
helm -n platform list
helm -n platform history quenching
```

回滚到上一版本：

```bash
helm -n platform rollback quenching        # 回滚到上一 REVISION
```

> **不要直接跑 `deploy.sh` 来更新**：它在未传环境变量时会随机重新生成密钥，并做 install/全量动作，日常更新请用上面的 `helm upgrade --reuse-values`。

## 6. 日常状态与排障命令

### 6.1 看整体状态

```bash
kubectl -n platform get pods                       # 所有 Pod 状态
kubectl -n platform get svc                        # Service 列表
kubectl -n platform get deploy                     # 所有 Deployment
kubectl -n platform top pod                        # 各 Pod 资源占用（需 metrics）
df -h /data                                        # 磁盘占用
```

### 6.2 看日志

```bash
kubectl -n platform logs deploy/content-service              # 当前日志
kubectl -n platform logs -f deploy/content-service           # 持续跟踪
kubectl -n platform logs deploy/content-service --previous   # 上一次崩溃前的日志
kubectl -n platform logs deploy/content-service --since=30m  # 最近 30 分钟
```

### 6.3 进入容器 / 在容器内执行命令

```bash
kubectl -n platform exec -it deploy/content-service -- sh
kubectl -n platform exec deploy/api-gateway -- printenv          # 查看全部环境变量
kubectl -n platform exec deploy/api-gateway -- printenv | grep ROUTE   # 查网关路由表
```

### 6.4 重启服务（不重建镜像时也可用于排除临时故障）

```bash
kubectl -n platform rollout restart deploy/<服务名>
kubectl -n platform rollout status  deploy/<服务名>
```

### 6.5 接口自测

在集群内直接访问服务（绕过网关鉴权）：

```bash
kubectl -n platform exec deploy/content-service -- \
  curl -s http://localhost:8082/api/v1/templates
```

从服务器经网关访问（无 token 时返回 401/鉴权类提示属正常；返回 `20004 路由不存在` 说明网关缺路由）：

```bash
curl -i http://localhost:30082/api/v1/templates
curl -i "http://<公网IP>:30080/api/v1/templates"
```

带登录 token 访问（将 `<TOKEN>` 换成登录后拿到的 JWT）：

```bash
curl -s "http://<公网IP>:30082/api/v1/templates" \
  -H "Authorization: Bearer <TOKEN>"
```

## 7. 常见问题速查

| 现象 | 排查方向 |
| --- | --- |
| helm 报 `localhost:8080 connection refused` | 未设置 KUBECONFIG，见 §1 |
| 接口返回 `{"code":20004,"msg":"路由不存在"}` | 网关路由表缺该前缀，请求在网关被挡、后端无日志；在 `deploy/helm/templates/_helpers.tpl` 补路由后 `helm upgrade --reuse-values` |
| 页面数据是旧的 / 领域计数对不上 | 镜像未更新：`git pull` 只改宿主机源码，需重建镜像并 `rollout restart`（模板文件是 COPY 进镜像的） |
| `ImagePullBackOff` | 镜像没导入 k3s，重跑 `images.sh`；查 `k3s ctr images ls \| grep quenching` |
| 改了代码重启后不生效 | tag 固定 `0.1.0`，必须重建镜像 + `rollout restart` |
| 迁移 Job 失败 | `kubectl logs job/migrate-<服务> -c migrate`，修复后 `migrate.sh clean` 再重跑 |
| 全员突然掉线/需重新登录 | 多半是 JWT_SECRET 被换；用 `--reuse-values` 或显式传入原密钥可避免 |
| 公网打不开但 Pod 正常 | 先 `curl http://localhost:30080`，通则是安全组未放行对应端口 |

## 8. 一次完整更新的操作顺序（备忘）

涉及近期统一资源池与弹性伸缩版本时，优先按 [近期升级说明](近期升级说明.md) 执行；下方仅为普通更新示例。该版本需先清理旧班次、应用新增迁移和升级 Helm/RBAC，确认旧 fault-engine 实例退出后再开放入口。

以"后端有代码改动 + 新增了迁移 + 前端也有改动"的最复杂情况为例：

```bash
# 0) 准备
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
cd /data/src/quenching && git pull

# 1) 构建有改动的镜像（迁移文件在镜像内，必须先构建）
cd deploy/server
bash images.sh training-service web

# 2) 跑数据库迁移（旧 Job 可能已经 Completed，先清理）
bash migrate.sh clean
bash migrate.sh

# 3) 重启使用新镜像的服务
kubectl -n platform rollout restart deploy/training-service deploy/web
kubectl -n platform rollout status  deploy/training-service
kubectl -n platform rollout status  deploy/web

# 4) 若本次还改了 deploy/helm/（如路由），再执行（只改镜像时不需要）
cd /data/src/quenching
helm upgrade quenching ./deploy/helm -n platform --reuse-values

# 5) 验证
kubectl -n platform get pods
curl -i "http://<公网IP>:30082/api/v1/templates"
```

## 9. 资源池与服务器扩展

后台“沙箱管理 → 资源池”按平台整体和每次实训汇总资源。申请量、尚未落地的预留、实际使用和 PVC 申请分别查看；没有完整指标时实际使用显示未采集，PVC 申请不代表物理磁盘剩余量。功能验证见 [实训验证指南](../../docs/testing.md)。

### 加入现有集群

新增服务器应接入现有 Kubernetes 集群。准备内网互通、独立节点名、兼容的 K3s 版本和镜像获取方式；不要在新服务器运行本仓库的单机 bootstrap 去创建另一套独立集群。K3s agent 使用现有 server URL 和加入令牌接入，按 [K3s 加入节点说明](https://docs.k3s.io/quick-start)操作，加入令牌不提交到仓库或填写到资源池后台。

当前 `images.sh` 只把镜像导入执行机器。多节点需要将相同版本镜像分发并导入每个节点，或统一使用各节点可拉取的镜像仓库；私有仓库配置参考 [K3s 私有镜像仓库说明](https://docs.k3s.io/installation/private-registry)。

```bash
NODE_NAME='<新节点名>'
kubectl get nodes -o wide
kubectl describe node "$NODE_NAME"
kubectl get pods -A -o wide
```

节点 Ready 且允许调度后，资源池刷新时会自动发现并计入容量，无需在数据库手工登记。新容量不会自动搬迁已有 Pod；创建新的实训检查实际落点。local-path/hostPath 卷绑定节点，新机器不会自动迁移旧机器上的本地卷；镜像缺失、卷拓扑和亲和性导致的 Pending 通过 Pod Events 排查。

### 调度、移除与资源调整

- 停止调度保留已有任务，不会自动排空、重启或关闭服务器。移除前先按集群流程迁移任务并断开节点，防止 kubelet 再次注册；后台只允许移除已 NotReady、停止调度、无关联 Pod 和本地卷的普通工作节点，控制平面由集群运维流程处理。
- 旧 `resource_version` 操作冲突返回 409，刷新后重新核对。后台修改平台容器资源可能滚动重启，需同步到自己的 Helm 覆盖配置，避免下次部署覆盖。
- 自动伸缩仅使用已加入资源池的服务器，受指标完整性和可用容量限制。资源故障期间自动调整冻结，清理确认后才恢复；手工修改和外部 HPA/VPA 仍可能改变训练条件，应在隔离环境核对。
