## 与以前的区别

| 项目 | 本次要求 |
| --- | --- |
| 环境 | 沿用现有 k3s、Docker、Helm、PG，无需重装或新建集群 |
| 镜像 | 不能只 git pull 或 restart；重建平台镜像，模板文件也打包在 content-service / sandbox-service 内 |
| 数据库 | 按依赖串行执行 migrate.sh；本次 content-service 到 6、training-service 到 27、sandbox-service 到 12。更旧版本也会补齐已有迁移 |
| Helm | 必须升级 chart，才能更新资源池路由、PriorityClass、资源声明和 sandbox-service 读取 metrics/HPA/VPA 的 RBAC |
| 升级窗口 | 暂停入口、正常结束并清理旧班次、停全部旧平台后端、备份 PG，再迁移和启动新版；禁止新旧版本混跑 |
| 伸缩指标 | metrics.k8s.io 必须提供有效 Pod 指标才能伸缩；缺失时保留当前资源，后台显示未知 |
| 故障保护 | 资源故障前检查内部冻结接口；令牌、权限或连接异常会拒绝执行，不允许绕过 |
| 模板与故障 | 更新模板镜像及清单后，故障绑定的 template_digest 要重新验收；不要直接沿用旧验收证据 |
| 多机 | 新机器加入原集群；平台和模板镜像须分发到各节点，本地卷不会自动迁移 |

## 现有服务器的操作顺序

先暂停对外新班次入口，让存量班次通过平台正常结束并清理；确认没有执行中的故障与待完成资源调整。入口暂停沿用你的现有代理/运维方法，现有脚本没有自动暂停入口的功能。此步骤不要用删除 PG 数据或批量删除沙箱代替。

本次将故障/坑点/组合配置迁到内容域，操作源时间线迁到沙箱域，训练域改为可靠工具日志和分析投影。迁移复制历史 ID、序列、软删除、证据；旧表保留但不再由应用读写。管理员配置修改、助手、后台扫描器也会写这些数据，所以仅暂停新班次还不够，必须停止旧后端后再复制。先等待进行中的复盘任务完成，保持 PG、Redis、RabbitMQ 和观测组件运行。

以下按默认平台 tag `0.1.0` 演示；已有自定义镜像仓库/tag 要保持与实际 release 一致。累积近期多个版本的改动时建议构建全部平台镜像，避免遗漏助手、复盘、网关和模板读取服务。

```bash
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
cd /data/src/quenching
git pull --ff-only

# 平台镜像及镜像内的迁移、模板文件
cd deploy/server
bash images.sh

# 保存原副本数，再停止旧平台后端（不停止数据库/消息队列）
# 以下按默认八个后端 Deployment 演示；已关闭/改名服务按实际列表调整。
upgrade_dir="$(mktemp -d /data/quenching-upgrade.XXXXXX)"
for service in api-gateway content-service user-service training-service review-service fault-engine sandbox-service ai-service; do
  kubectl -n platform get deployment "$service" \
    -o jsonpath='{.metadata.name}{" "}{.spec.replicas}{"\n"}' >> "$upgrade_dir/replicas.txt"
done
kubectl -n platform scale deployment api-gateway content-service user-service training-service review-service fault-engine sandbox-service ai-service --replicas=0
# 等待 Helm 平台后端 Pod 全部退出；失败时保持停机，勿执行迁移。
kubectl -n platform wait --for=delete pod \
  -l 'app.kubernetes.io/instance=quenching,app.kubernetes.io/component in (api-gateway,content-service,user-service,training-service,review-service,fault-engine,sandbox-service,ai-service)' \
  --timeout=10m
kubectl -n platform get pods

# 停写后备份整个数据库，备份文件留在服务器目录，并验证 dump 可读
kubectl -n platform exec postgresql-0 -- pg_dump -U quenching -d quenching -Fc > "$upgrade_dir/quenching.dump"
test -s "$upgrade_dir/quenching.dump"
kubectl -n platform exec -i postgresql-0 -- pg_restore --list < "$upgrade_dir/quenching.dump" > "$upgrade_dir/backup-contents.txt"
test -s "$upgrade_dir/backup-contents.txt"

# 旧 Completed Job 不能执行新迁移，先删除旧迁移 Job 再创建
bash migrate.sh clean
bash migrate.sh

# 升级 chart，复用服务器已有密钥和配置
cd /data/src/quenching
helm upgrade quenching ./deploy/helm -n platform --reset-then-reuse-values --wait --timeout 10m

# 恢复升级前的副本数（包括自定义扩容数量）
while read -r service replicas; do
  kubectl -n platform scale deployment "$service" --replicas="$replicas"
done < "$upgrade_dir/replicas.txt"

# 同步基础设施与前端的资源/优先级清单
kubectl apply -f deploy/server/manifests/01-rbac.yaml
kubectl apply -f deploy/server/manifests/10-middleware.yaml
kubectl apply -f deploy/server/manifests/15-gateway.yaml
kubectl apply -f deploy/server/manifests/20-frontend.yaml

# 固定 tag 不变时，Helm 可能没有触发新镜像启动，显式重启并等待
for service in api-gateway content-service user-service training-service review-service fault-engine sandbox-service ai-service web admin; do
  kubectl -n platform rollout restart deployment/"$service"
  kubectl -n platform rollout status deployment/"$service" --timeout=10m
done

kubectl -n platform get pods
kubectl get priorityclass quenching-platform quenching-training
kubectl top pods -n platform
```

每一步成功后再执行下一步；发生错误先排查，保持入口暂停和旧写入者停机。`migrate.sh clean` 只删除迁移 Job，不清空数据库，也不执行 down。脚本按 fault-engine → training-service → user-service → content-service → sandbox-service → review-service 创建并等待 Job，前一个失败就停止。首次安装也必须用这个顺序；`render` 输出的全部 Job 不能一次性 apply 来代替脚本。

迁移 Job 全部完成后才能启动新版服务。核对三个迁移表分别为版本 6、27、12，且没有 dirty 标记：

```bash
kubectl -n platform exec postgresql-0 -- psql -U quenching -d quenching -c \
  'SELECT version,dirty FROM schema_migrations_content_service; SELECT version,dirty FROM schema_migrations_training_service; SELECT version,dirty FROM schema_migrations_sandbox_service;'
```

本次属主迁移的 down 会主动拒绝执行，不能迁移后直接回退旧镜像：新版本的写入不会自动同步回旧表。需要回滚时保持入口暂停，停止全部后端，从本次停写备份恢复整库，再部署对应旧镜像/Chart；这会丢失备份之后的新写入，应先保存故障现场和新增数据。不要用 `force` 清除 dirty 或手工改版本号掩盖失败。

`--reset-then-reuse-values`（本仓库引导版本 Helm 3.16.3 支持）先加载新版 Chart 默认值，再合并上次保存的配置和本次覆盖项，既补齐新配置项，也保留已有密钥、显式资源申请和日志挂载设置。对照 `deploy/helm/values.yaml` 审查旧 requests/limits、logging.persistence 等设置，需要调整时使用你自己的覆盖文件，仅写要改变的项。新版默认 stdout；原有日志 PVC 保留，跨节点共享文件日志需要 RWX 存储。不要直接追加带占位密钥的 `values-server.yaml` 覆盖生产配置。

目前 `deploy.sh` 默认重新生成 JWT_SECRET / INTERNAL_TOKEN，并重新应用首装 values；普通升级使用上面的 Helm 命令。该脚本的 INTERNAL_TOKEN 目前只覆盖 observability.wsGatewayApiKey，首装时须像 README 一样同时显式设置 global.internalToken。现有有效密钥不要因本次升级随意更换。

mall 业务镜像与平台镜像是两组产物。首次接入，或者本次更新包含 mall 的 Java/Vue/初始化 SQL 适配时，在开放 mall 班次前执行：

```bash
cd /data/src/quenching
bash templates/mall/scripts/build-images.sh
```

这个脚本不会由 `images.sh` 代执行。模板默认 tag 为 `mall-0.1.0`，若修改 tag 需同步模板 chart 后重新构建平台镜像。多节点必须先完成平台与模板镜像分发，不能只导入构建节点。

确认所有滚动更新已完成、旧 fault-engine Pod 已退出，再恢复入口并用新班次验收。已有资源故障不应跨版本继续运行。

## 功能前提与验收入口

- 资源池/伸缩读取 Kubernetes metrics；Prometheus 提供的业务观测不能替代 metrics.k8s.io。不需要安装 HPA/VPA 控制器，本次伸缩由 sandbox-service 自己控制；VPA 未安装返回 404 可以接受，读取权限错误则不能注入资源故障。
- fault-engine 的 sandbox_service.base_url 和各服务 internal.token 由 chart 渲染；保持 global.internalToken 与 observability.wsGatewayApiKey 一致，内部冻结端点不开放公网。
- `faultExecution.enabled` 仍由你原有 values 控制，本次升级不自动开启真实故障执行；启用前需完成已有 ChaosBlade 前提和候选故障验收。模型凭证沿用原来的服务配置，不需因资源池修改重新申请。
- 资源故障期间沙箱和平台 fault-engine 的自动调整冻结；确认所有叠加故障清理后再恢复。管理员手工调整尚不具备自动控制器的完整容量预留保证。
- 详细验证：[实训、资源池与故障冻结](../../docs/testing.md)、[mall 模板加载](../../templates/mall/SERVER_DEPLOY.md)。mall 加载通过不等于交易、故障和整班次复盘已经验收。
- 本次归位验收：后台新增/修改故障和坑点能保存并被新班次读取；故障运行时读取配置、助手工具、用户操作上报、班次内记忆和一次完整班次复盘可用。暂时停止 training-service 后沙箱投递应保留，恢复后补齐；投递未补齐的封存报告应标明缺口。内部接口必须带既有令牌，原有管理员权限保持生效。成功上报操作后立即结束，最终评分必须包含这些操作；投影未收到确认时暂不落最终分，正常修复且已完成的班次在30秒后自动补试，恢复投递后应补评分。新操作单条 detail 不超过7MiB；历史超大记录通过已迁移完整副本的摘要确认，原始证据不截断。

## 构建中断后的重试（2026-10-12）

如果 training-service 构建提示 `updates to go.mod needed`，这是源码依赖声明不完整，不是服务器缺少 Go。修复版本补齐 training-service 的 uuid 直接依赖及 sandbox-service 的 JWT 依赖/校验条目，拉取修复后重新运行：

```bash
cd /data/src/quenching
git pull --ff-only
bash deploy/server/images.sh
```

`images.sh` 在所有目标构建成功后才统一导入 k3s；中途失败时先前构建成功的镜像可能仍只在 Docker 中。因此重跑完整命令，让已有构建缓存复用，并完成全部镜像导入，再继续迁移和 Helm 升级。无需在服务器安装 Go 或手工运行 go mod tidy。

发布前的 Go 构建核对必须关闭 go.work，使用镜像同样的 `GOWORK=off GOOS=linux CGO_ENABLED=0` 与 readonly 模块模式；工作区模式下的 Go 回归不能单独证明镜像可构建。本次本地核对使用缓存工具链与模块，不代表已实际运行 Docker 镜像或部署到服务器。

## sandbox-service 路由冲突导致升级超时（2026-10-14）

若迁移已经成功，其他后端就绪，但 sandbox-service 为 CrashLoopBackOff，日志提示 `/internal/v1/sandboxes/:id/behavior/commands` 与 `:session_id` 冲突，原因是 Gin 同一方法的路径树不能在相同位置注册不同的通配参数名。修复统一内部行为命令、runner、支付路由的参数名，并保持实际 HTTP 请求地址和认证方式不变。

下面适用于已完成迁移、八个后端目标副本数为 1、平台镜像 tag 为 `0.1.0` 的本次单机升级。只重建修复的沙箱服务镜像；使用同一 tag 导入后先重启该服务，等它就绪，再重新提交 Helm 升级，使 release 状态恢复为 deployed。上一次升级命令使用 `set -e`，超时后没有执行前端更新，所以最后补上前端步骤。

```bash
(
  set -euo pipefail
  export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
  cd /data/src/quenching

  git pull --ff-only
  IMAGE_TAG=0.1.0 bash deploy/server/images.sh sandbox-service

  kubectl -n platform rollout restart deployment/sandbox-service
  kubectl -n platform rollout status deployment/sandbox-service --timeout=5m

  helm upgrade quenching ./deploy/helm -n platform \
    --reset-then-reuse-values \
    --set global.imageTag=0.1.0 \
    --set services.sandbox-service.replicas=1 \
    --wait --timeout 10m

  kubectl apply -f deploy/server/manifests/20-frontend.yaml
  kubectl -n platform rollout restart deployment/web deployment/admin
  kubectl -n platform rollout status deployment/web --timeout=5m
  kubectl -n platform rollout status deployment/admin --timeout=5m

  helm status quenching -n platform
  kubectl -n platform get deployments,pods
)
```

本次恢复无需重新执行数据库迁移或重建 mall 镜像。若任何步骤失败，停止后续步骤并收集对应 Pod 日志。平台恢复后，仍须创建真实 mall 沙箱并按 [mall 模板加载验收](../../templates/mall/SERVER_DEPLOY.md) 验证。

## 项目管理缺列与移除静态演示模板（2026-10-14）

线上旧项目表缺少 `description`、`architecture_image`、`difficulty`，项目列表、详情及创建/编辑会报内部错误。content-service 000006 以默认值补齐三列，保留现有项目；回退版本也保留这些字段与管理员填写的数据。后台项目管理新增官方模板列表，通过目录扫描接口读取，并将登记项目单独展示。故障页分别处理模板与登记项目的加载结果；一个来源失败时仍可使用另一来源，错误提示可重试。

官方模板的“查看故障”带入模板筛选，故障的“配置坑点”带入故障 ID，新建坑点自动填入此 ID。旧坑点保持原有故障关联，不能把它们当作 mall 已适配配置。静态演示模板已删除，官方目录当前只保留真实开源 mall。

现有平台已完成前面属主迁移且服务就绪时，按以下增量流程升级。需要重建 content-service / sandbox-service 内的模板目录和 admin 前端。000006 是加列迁移，无需重新停掉全部后端；先成功迁移，再启动新镜像。

```bash
(
  set -euo pipefail
  export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
  cd /data/src/quenching

  git pull --ff-only
  IMAGE_TAG=0.1.0 bash deploy/server/images.sh content-service sandbox-service admin

  kubectl -n platform delete job migrate-content-service --ignore-not-found
  bash deploy/server/migrate.sh
  kubectl -n platform exec postgresql-0 -- psql -U quenching -d quenching -c \
    'SELECT version,dirty FROM schema_migrations_content_service;'

  kubectl -n platform rollout restart deployment/content-service deployment/sandbox-service deployment/admin
  for service in content-service sandbox-service admin; do
    kubectl -n platform rollout status deployment/"$service" --timeout=5m
  done
  kubectl -n platform get deployments,pods
)
```

预期 content-service 迁移版本为 6、dirty=false。迁移脚本串行检查所有服务，已到最新版本的服务保持原版本。这里仅删除旧 content-service 迁移 Job，使它复制新版镜像中的 000006 并执行；不清空任何业务表。

刷新后台与用户端列表，确认 mall 显示、静态演示项目消失。验证登记项目列表不再报错，模板故障筛选与坑点关联 ID 正确。这个增量流程无需重建 mall 的业务镜像，商城真实沙箱加载仍按模板验收文档执行。
