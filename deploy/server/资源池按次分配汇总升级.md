# 资源池按次分配汇总升级（2026-10-31）

## 展示与统计口径

资源池主视图按完整的分配对象展示：平台整体一项，每个活跃实训／沙箱各一项，集群基础设施单独汇总。服务、容器和弹性策略放在对应对象的展开明细中，仍可按原权限调整资源与策略。

- **已申请**：当前集群中该对象全部非终态 Pod 的 CPU／内存申请。滚动部署时统计实际存在的 Pod，不按工作负载的目标副本数推算。
- **未落地预留**：已经获准、但尚未体现为 Pod 申请的资源。来自现有准入和弹性调整预算，不能重复叠加沙箱资源计划。
- **本次占用**：已申请与未落地预留之和，表示调度层的资源占用。
- **实际使用**：来自 Pod 指标。缺失、过期或只有部分 Pod 指标时显示未知及采集覆盖情况，不能把部分数据或资源计划当成实际使用量。
- **存储申请**：该对象实际 PVC 的申请量；沙箱资源计划中的存储预算单独展示，不作为实际磁盘用量。
- **已配置上限合计**：当前 Pod 已配置资源上限的汇总，不表示没有配置上限的容器也受此合计限制。班次计划上限另外展示。

排队中、尚未准入的班次仍保留一项，显示需求计划，不把计划计为已占用。未关联活跃班次记录的沙箱命名空间资源也会单独保留，避免遗留资源从资源池页面消失。

资源故障冻结仍按原有班次规则生效。页面汇总不新增整体伸缩开关；展开明细后沿用各服务原有的策略开关、版本冲突检查和资源编辑。

## 部署

本次没有数据库迁移或新增 Kubernetes 权限。需同时更新 `sandbox-service` 与 `admin`；接口新增 `allocation_units` 汇总数据，原字段保留。仅更新后台前端时，旧后端无法提供汇总数据，页面会提示更新后端。

```bash
(
  set -euo pipefail
  export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
  cd /data/src/quenching
  git pull --ff-only

  IMAGE_TAG=0.1.0 bash deploy/server/images.sh sandbox-service admin

  kubectl -n platform rollout restart deployment/sandbox-service deployment/admin
  for service in sandbox-service admin; do
    kubectl -n platform rollout status deployment/"$service" --timeout=10m
  done
)
```

## 验收

1. 无实训时，默认看到平台整体及基础设施汇总，不再铺开每个服务的资源卡片。
2. 同时开启两个沙箱，应出现两条独立班次汇总；模板相同、用户相同也不能合并成一条。
3. 排队班次展示计划需求；部署中班次展示已申请及剩余预留，两者相加构成本次占用，不重复计算完整计划。
4. 结束一个班次后检查其资源回收；其他班次与平台汇总独立变化。仍存在的未关联沙箱资源不能被隐藏。
5. 展开平台或班次明细，检查服务资源、弹性策略及冻结状态；原有资源编辑、策略开关和节点管理仍可正常使用。
6. 指标缺失时显示未知／采集不完整；PVC 申请与计划存储预算分别展示。

本地验证使用 Kubernetes 假客户端、服务回归及浏览器模拟接口。真实集群的资源变化、伸缩收敛和班次回收需在服务器验收。
