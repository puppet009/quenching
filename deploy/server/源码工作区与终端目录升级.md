# 源码工作区与终端目录升级（2026-10-29）

适用现有 `quenching` release、`platform` 命名空间和单机 k3s。平台镜像沿用 `0.1.0`，商城镜像升级为 `mall-0.2.0`。无需平台数据库迁移；本次需要重建商城前后端业务镜像。

## 使用方式

| 服务 | 终端默认目录 | 部署目录 | 配置目录 |
| --- | --- | --- | --- |
| frontend | `/workspace/mall-app-web` | `/usr/share/nginx/html` | `/etc/nginx/conf.d` |
| mall-portal | `/workspace/mall` | `/app` | `/app/config` |
| mysql | `/var/lib/mysql` | — | — |
| redis | `/data` | — | — |
| rabbitmq | `/var/lib/rabbitmq` | — | — |
| mongo | `/data/db` | — | — |

终端显示实际工作目录；`cd` 后文件列表跟随，已打开编辑器的草稿保留。“项目 / 部署 / 配置”入口只浏览文件，不向终端注入命令。源码根目录附有 `TRAINING.md`。

保存前后端源码后运行 `training-rebuild`（别名 `mall-rebuild`），使用镜像缓存离线构建并发布。Java 构建时暂停 JVM，失败时重新启动上次发布的 JAR；前端构建失败不覆盖运行中的站点。构建成功后还需等待健康检查、验证真实业务。

模板通过 Pod 注解 `quenching.io/terminal-directories` 按容器声明 `working_dir`、`deployment_dir`、`config_dir`。平台校验绝对路径，不硬编码 mall 名称；旧模板回退到 Pod workingDir 或容器原始目录。终端目录独立于应用主进程工作目录。

新增两个班次独立的工作区 PVC，共六个 PVC。源码、可编辑配置与发布结果在容器重启后保留，结束后随 namespace/PVC 回收；StorageClass 仍需 Delete 策略。两个业务服务暂为单副本，避免 RWO 卷与并发构建冲突。

前端 Node 堆上限640Mi、容器上限1Gi；Java 构建时 Maven 堆上限384Mi、容器仍为768Mi。源码构建内存计入资源池申请，避免仅按空闲服务占用接纳过多班次。加入行为引擎后资源声明为625m CPU/2976Mi内存，硬限额4核/5Gi，存储5536Mi。实际使用以资源池监控为准。

## 升级

先在页面结束当前测试实训，再整块执行。业务镜像构建需要 npm、Maven、Alpine 包源和镜像源；运行时构建使用缓存。多节点按原流程分发镜像。

```bash
(
  set -euo pipefail
  export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
  cd /data/src/quenching
  git pull --ff-only

  MALL_IMAGE_TAG=mall-0.2.0 bash templates/mall/scripts/build-images.sh
  IMAGE_TAG=0.1.0 bash deploy/server/images.sh web content-service sandbox-service

  helm upgrade quenching ./deploy/helm -n platform \
    --reset-then-reuse-values --wait --timeout 10m

  kubectl -n platform rollout restart deployment/content-service deployment/sandbox-service deployment/web
  for service in content-service sandbox-service web; do
    kubectl -n platform rollout status deployment/"$service" --timeout=10m
  done
)
```

刷新页面并新建 mall 实训。旧班次不会被强行换镜像、挂新卷或覆盖修改。模板运行指纹已改变，故障需按新指纹重新验收。

## 服务器验收

1. 前后端执行 `pwd`、`ls`，确认上表目录、真实源码与 `TRAINING.md`；终端切换目录后文件地址一致，切换服务器/容器不串目录。
2. 打开源码编辑器保留未保存草稿，在终端切换目录，确认草稿仍在；“部署 / 配置”可定位真实运行文件。
3. 修改一处页面文本或 Java 接口，运行 `training-rebuild`，确认页面/接口真正改变。新增未缓存依赖不属于离线构建范围。
4. 编译错误必须非零退出并继续使用上次发布结果；修复后能重建。删除/改名源码和资源后，旧生成文件不得继续打包。
5. 在测试班次验证容器重建后源码、配置、成功发布结果仍在；结束并确认六个 PVC 回收，再建新班次确认恢复初始源码和业务数据。
6. 检查操作证据与复盘。交互终端仍提示逐条命令/退出码的覆盖限制；完整命令证据使用平台“命令执行”。

本地验证包括脚本参数、成功/失败发布、并发/中断、初始化/保留、真实 xterm 与文件面板交互（模拟 API/WS）。本地无 Docker/k3s，真实镜像构建、Vue/Java 编译、服务启动、资源实测和物理卷回收仍需服务器验收。
