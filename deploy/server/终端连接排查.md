# 实训终端连接排查（2026-10-27）

## 本次现场结论

班次 8 的商城服务已启动，终端连接持续重试。以 `platform/sandbox-service` 身份实际执行容器命令时返回：

```text
cannot create resource "pods/exec" in API group "" in the namespace "sandbox-8"
```

现场旧版 Helm 的 sandbox-ns 角色授予了普通 `pods` 权限，但没有 `pods/exec` 子资源权限。
终端、命令执行与文件操作使用 Kubernetes exec，普通 Pod 创建权限不能替代 exec 权限。

此前使用 `auth can-i create pods/exec` 得到 yes，因为该参数形式存在 `TYPE/NAME` 歧义。
检查子资源应显式使用 `--subresource=exec`，并指定本次沙箱命名空间：

```bash
KUBECONFIG=/etc/rancher/k3s/k3s.yaml kubectl auth can-i create pods --subresource=exec --as=system:serviceaccount:platform:sandbox-service -n sandbox-8
```

命令形式参考 [Kubernetes kubectl auth can-i 文档](https://kubernetes.io/docs/reference/kubectl/generated/kubectl_auth/kubectl_auth_can-i/)。

## 已完成的错误显示修复

- 服务端返回终端 error 帧后，用户端保留具体原因并停止自动重连；提供“重新连接”按钮。
- 正常退出 shell 后不自动重开；意外网络中断仍保留自动恢复。
- 手动重试建立新连接后，旧连接的迟到事件不会覆盖新状态。
- sandbox-service 记录“终端连接失败”，关联班次、Pod、容器和失败阶段；日志不包含 WebSocket token 或用户命令。
- 审计存储异常仍阻止终端继续执行，不绕过操作记录要求。审计启动和输入失败向浏览器显示通用错误，详细原因记服务端日志。

错误显示修复与下述班次授权修复一起部署。无需数据库迁移，不重建商城业务镜像。默认 tag 为 `0.1.0`；已有自定义 tag 时沿用现有值。更新命令：


## 每班次自动授权与回收

负责人已明确：每次实训在独立项目沙箱中拥有操作权限，实训结束后回收，下一次从模板基线重新创建。

- Helm 安装一个只包含 `pods/exec:create` 的 ClusterRole 权限模板，不为它创建 ClusterRoleBinding。
- 新增的 `bind` 委派仅允许引用这个指定模板；平台控制器在已校验班次 ID、归属标签的 `sandbox-<班次ID>` 内创建 `sandbox-project-access` RoleBinding。绑定对象是平台 sandbox-service 身份，浏览器用户仍由会话归属校验隔离。
- 新沙箱自动授权；服务重启后的调谐会为仍在运行的旧沙箱补齐授权。终端、文件管理和命令执行共用这份 exec 权限。
- `/complete` 成功前撤销本班次绑定的主体，并保留关闭标记；调谐也会撤销已完成/释放中的班次，旧任务不能重新授权。
- 授权创建持有沙箱记录的数据库行锁，与结束时间更新串行；即使结束时 namespace 还不存在，旧部署任务也不能在结束确认后再创建授权。行锁只覆盖基础资源创建，不覆盖整个商城部署等待。
- 已建立的终端在连接时及每 2 秒检查班次是否开放，结束后冻结并关闭连接。RBAC 撤销本身不会关闭已有 exec 流。
- 托管命令在启动前及运行期间检查工作区状态，结束后取消执行通道；被中断、无法确认退出码的命令保留 unknown 证据，不伪报执行成功。后台进程最终由 namespace 销毁终止。
- 销毁 namespace 时一并清理该班次 Pod、Secret、PVC 和 RoleBinding；模板镜像是下一班次的基线。StorageClass 必须使用 Delete 回收策略。实训记录与复盘证据按平台流程保存。

Kubernetes 的 namespace RoleBinding 可引用 ClusterRole，但授权仅在该 namespace 生效。基础资源调度控制器原有的集群管理权限仍存在，与本次动态 exec 授权分开；代码按班次标签约束创建绑定的位置。绑定管理需要对指定 ClusterRole 的 `bind` 权限，否则控制器即使能创建 RoleBinding，也会被 Kubernetes 的防越权检查拒绝。参见 [Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)。

升级后等待 sandbox-service 首轮调谐，再检查当前仍活跃的班次。下面以现场班次 8 为例；若它已结束，改用新的班次 ID、Pod 和容器名：

```bash
KUBECONFIG=/etc/rancher/k3s/k3s.yaml kubectl -n sandbox-8 get rolebinding sandbox-project-access -o yaml
KUBECONFIG=/etc/rancher/k3s/k3s.yaml kubectl auth can-i create pods --subresource=exec --as=system:serviceaccount:platform:sandbox-service -n sandbox-8
KUBECONFIG=/etc/rancher/k3s/k3s.yaml kubectl --as=system:serviceaccount:platform:sandbox-service -n sandbox-8 exec mall-portal-d699fd94c-hjsz8 -c mall-portal -- /bin/sh -c 'printf "terminal-exec-ok\n"; id'
# 平台命名空间不应因本次模板获得 exec 权限；预期 no。
KUBECONFIG=/etc/rancher/k3s/k3s.yaml kubectl auth can-i create pods --subresource=exec --as=system:serviceaccount:platform:sandbox-service -n platform
```

在页面手动“重新连接”。权限更新无需重建现有商城 Pod。随后在测试沙箱的 `/tmp/quenching-reset-check` 写入标记，结束整个实训；确认旧终端冻结、绑定 subjects 为空，随后 namespace/PVC/PV 被回收。新建下一班次，确认标记不存在、初始业务数据重新生成，另一个活跃班次不受影响。不要在生产共享目录或模板源码中做重置测试。

## 本地验证边界

前端回归覆盖服务端拒绝、正常结束、旧连接迟到消息、手动重试与网络中断恢复。后端回归覆盖按班次授权、归属校验、结束撤销、关闭后不再授权、其他班次隔离、终端冻结；Helm 渲染检查权限模板没有全局 exec 绑定、bind 只指向指定模板。
本地浏览器使用模拟 API/WebSocket 验证错误提示和手动恢复，不能代替真实集群 exec 验收。
数据库并发授权测试需设置 `TEST_DATABASE_URL`；未设置时会明确跳过，不能视为已通过真实 PostgreSQL 并发验收。
