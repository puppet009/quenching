# templates/ —— 官方预置实训模板

本目录只放**官方调研筛选的真实开源项目模板**。每个模板是一个以 slug 命名的子目录，
完成适配与验收后，通过清单在服务启动时自动发现，无需在数据库登记（当前不是目录热更新）：

- `content-service` 启动时扫描本目录，通过 `GET /api/v1/templates` 向前端提供模板列表；
- `sandbox-service` 按模板清单里声明的 Chart 路径，用 Helm 在沙箱命名空间内完成部署；
- `training-service` 等其他消费方只读取清单中的服务声明，不再硬编码服务名。

> 真实开源模板接入前，本目录允许为空：注册表扫描不到模板时返回空列表，各服务照常启动。

## 目录边界

- **这里只放官方预置模板**，且必须是调研筛选后的真实开源项目，不放自研靶场/演示代码。
- **用户自定义上传的项目不进本目录**：未来走对象存储（MinIO/OSS）+ 数据库登记，
  由模板注册表的另一种来源实现提供（接口见 `packages/go-common/templates`），
  消费方继续使用统一注册表接口。上传、自动识别、适配与验证能力属于后续工作，当前接口不代表这些能力已实现。

## 实训模板准入规范（第一版）

以下是正式开放模板必须满足的准入要求，不代表现有平台已实现全部支持。
候选真实开源项目可以先导入本目录，但必须在自己的 README 中标明“待适配、待验收”。
候选阶段不提供可发现的 `template.yaml`；完成部署适配后可用 `enabled: false`，验收通过后才启用。
负责人专用的加载验收环境可以在完成本阶段配置后使用 `enabled: true`，使平台能发现和部署；
接入进度、未支持能力与验收证据记录在模板 README 和 ACCEPTANCE 中，不作为用户详情页的项目介绍。
用户展示资料说明项目是什么、业务场景和训练目标；展示资料不等同正式实训准入，面向学员的正式环境仍应在完整验收前停用。
文件清单的语法校验不能替代实训准入验收。

| 准入项 | 要求与验收依据 |
| --- | --- |
| 真实来源 | 记录上游仓库、许可证、固定版本或 commit；保留许可证及版权声明，记录平台适配差异。不得用自研演示站替代真实电商项目。 |
| 统一接入 | 每个模板一个目录，目录名与 slug 一致；声明服务、部署配置、资源预算与健康检查，不要求消费方硬编码项目名称。 |
| 独立部署 | 项目及业务依赖运行在沙箱专属环境中，部署、初始化、失败清理可重复；用实测证明正常业务和模拟负载下满足平台资源限制。 |
| 真实业务 | 声明并跑通实际支持的交易链路，如浏览、加购、下单、库存扣减、支付、取消和查单；不可用页面成功提示代替订单落库和数据一致性验证。不同模板可以覆盖不同业务。 |
| 模拟用户 | 每次新沙箱由平台模拟用户引擎走项目真实注册流程创建账号，再执行业务操作；模板提供入口、交互适配和必要商品、库存等初始化数据。确需管理员时只在本次沙箱初始化创建。 |
| 外部隔离 | 支付、短信、邮件、物流等外部依赖声明替换方式，接入沙箱内模拟服务；保留真实请求、响应和回调语义。平台限制网络出口，防止真实扣款、发送或生产服务调用。 |
| 故障适配 | 每个模板绑定一批适用且经过验证的故障，声明组件、业务能力及适配信息。故障定义与绑定由后台统一管理，不在模板目录维护第二份故障库。 |
| 恢复验证 | 每个故障有明确的系统及业务恢复判据；中间件也可成为训练对象。不能只凭服务存活、用户点击完成或 AI 判断认定修复。 |
| 过程复盘 | 平台记录模拟行为、故障事件、学员操作、代码与配置修改及运行证据，关联班次和挑战，形成可供 AI 复盘的时间线。 |
| 完整重置 | 同一班次内保留修改，支持动态增加或叠加故障；结束先保存复盘证据，再销毁运行环境及账号、订单、数据库、缓存、消息、文件、模拟服务状态和代码修改。下一班次从固定源码和初始化数据重新开始。 |

### 模板、大脑与故障管理的边界

- 模板负责提供真实业务系统、部署与操作适配、可验证的业务结果；平台提供模拟用户引擎、外部依赖模拟服务、证据采集和沙箱生命周期。
- AI 大脑根据已经验证的学员表现，在同一班次调度模拟行为和故障；模板 `difficulty` 仅描述基础复杂度，不固定每轮挑战难度。
- 用户选择模板时可以知道故障范围和训练目标，但不知道本班次具体触发时间、目标、强度及组合。
- 每个模板只覆盖自身适用的一批故障，各类故障由整个模板库逐步覆盖。共享故障机制与项目适配分开，保留后续自定义项目自动适配的空间。
- 故障必须对应真实事故或已确认问题，后台保留原始来源、适用条件、触发方式、预期现象、恢复判据和清理方式。不得假定所选上游版本含有未确认的缺陷。
- 多故障组合必须验证可分辨、可修复；训练组合应明确标注，不冒充有真实来源的复合事故。
- 外部模拟服务由平台统一提供，状态按沙箱隔离；支付需走创建订单、发起支付、模拟结果、回调及订单更新链路，不以直接修改订单状态代替支付流程。

### 正式启用前的验收记录

每个模板维护 `README.md`、`SOURCE.md`（源码来源及适配差异）和 `ACCEPTANCE.md`（验收记录）。
来源等准入信息当前以文档保存，不假定尚未支持的 YAML 扩展字段能被平台使用。
验收记录至少覆盖：

1. 固定源码、许可证和前后端配套关系核对。
2. 从新沙箱启动到注册、正常交易及业务数据验证的完整流程。
3. 资源占用、必要依赖、外部调用隔离及模拟回调的实测。
4. 已公开故障逐条触发、修复、恢复验证和清理；开放组合另行验证。
5. 同一班次多轮挑战保留修改，班次结束保存证据后清空运行状态。
6. 连续启动两个新班次，证明无账号、订单、库存变动或代码修改跨班次残留。

记录固定版本、运行环境、命令、结果和证据位置。未验证项保持“待验证”，不能以文档或源码初筛代替实跑通过。

## 模板目录结构

```
templates/
└── <slug>/                 # slug 即模板唯一标识，也兼作 Helm release 名
    ├── README.md           # 接入状态、业务能力与操作说明
    ├── SOURCE.md           # 上游仓库、固定 commit、许可证与适配差异
    ├── ACCEPTANCE.md       # 验收结果与证据；待验证项明确标注
    ├── upstream/           # 可选，保留许可证的上游源码
    ├── template.yaml       # 可部署阶段必需；候选导入阶段暂不提供
    ├── catalog.yaml        # 可选，用户展示名称、简介、场景、训练目标及组件说明
    ├── catalog-assets/     # 可选，用户展示封面和内部来源记录；不作为沙箱运行制品
    └── helm/               # Helm Chart（目录名由清单 chart 字段声明）
        ├── Chart.yaml
        ├── values.yaml
        └── templates/
```

## template.yaml 规范（apiVersion: quenching/v1）

```yaml
apiVersion: quenching/v1     # 必填，当前固定为 quenching/v1
slug: mall                   # 必填，^[a-z0-9]([a-z0-9-]{0,38}[a-z0-9])?$，1-40 字符
name: 电商交易系统             # 必填，前端展示名
domain: ecommerce            # 可选，业务领域标签
description: 一句话简介       # 可选
difficulty: medium           # 可选，模板基础复杂度，easy | medium | hard；非班次动态难度
tech_stack: [Go, MySQL, Redis]  # 可选
chart: helm                  # 必填，模板目录内的 Chart 相对目录（必须存在）
sort_order: 100              # 可选，列表排序权重，升序；缺省 0
enabled: true                # 可选，缺省 true；false 时列表隐藏且按不存在处理
services:                    # 必填，至少 1 个，name 唯一
  - name: user-service       # 服务名（前端展示/评分关联键）
    workload: user-service   # 可选，K8s Deployment/StatefulSet 名，缺省取 name
    port: 8080               # 可选，服务端口
    role: business           # 可选，business（默认）| middleware；当前通用评分忽略 middleware
  - name: order-service
    workload: order-service
    port: 8081
    role: business
images:                      # 可选，需要构建私有镜像的服务；全走公共镜像则省略整段
  - name: order-service      # 必须与 services[].name 对应
    context: .               # 模板目录内的构建上下文
    dockerfile: Dockerfile
resources:                   # 可选，单个沙箱实例的总资源预算（预检/配额用）
  cpu: "2"
  memory: "4Gi"
```

### 校验规则

注册表加载时对每个模板执行校验，**坏模板只跳过自身并打印 warn 日志，不影响其他模板与服务启动**：

1. `apiVersion` 必须是 `quenching/v1`；
2. `slug` 符合正则且在所有模板中唯一（重复时保留目录序在先者，后者跳过）；
3. `name`、`chart` 非空，且 `chart` 必须是模板目录内的相对路径（禁止绝对路径与 `..` 逃逸），指向的目录必须存在；
4. `difficulty` 若给出必须在枚举内；
5. `services` 非空、`name` 非空且唯一；`workload` 缺省补为 `name`，`role` 缺省补为 `business`；
6. `images[].name` 必须能在 `services` 中找到，`context`/`dockerfile` 非空。

## catalog.yaml 用户展示资料（可选）

用户页面介绍项目本身及训练价值，接入阶段、部署待办和验收记录保留在维护文档中。
注册表在完成清单校验和运行制品指纹计算后加载展示资料，列表与详情接口返回同一份资料。
没有该文件时沿用 `template.yaml` 的名称和简介；文件无效时记录 warn 并回退，不阻断原模板加载。

```yaml
name: 电商交易实训
description: 基于真实电商项目，围绕商品与订单链路开展故障排查练习。
cover:                      # 可选，只配置一张封面，不轮播
  file: home.png            # catalog-assets/ 内的 PNG/JPEG 文件名
  alt: 商城首页
overview:
  - 介绍真实业务链路、组件关系以及训练关注的工程问题。
audience:
  - 掌握基础开发、希望提升独立排障能力的工程师。
business_scenarios:
  - 商品浏览与详情查询
  - 购物车与订单处理
learning_objectives:
  - 结合业务现象、日志和监控定位问题。
  - 提出修复方案，验证恢复并复盘排查路径。
services:
  user-service:             # 必须是 template.yaml 中已声明的服务名
    display_name: 用户服务
    description: 承载用户相关业务接口。
```

`name` 和 `description` 必填，其余字段可选。封面为单张 PNG/JPEG，要求真实普通文件、不超过 2MiB、单边不超过 4096 像素，提供有意义的 alt 文本。
文件及资源目录不允许符号链接；封面文件名不允许路径分隔符或目录跳转。无封面时使用原领域渐变，图片加载失败时同样回退。
展示资料文件必须为普通文件，字段采用严格校验，
服务键必须与清单对应；不允许添加 `enabled`、端口、工作负载或其他运行配置。
`catalog.yaml` 和 `catalog-assets/` 只影响展示，不参与运行制品指纹，不改变部署、启用状态或故障验收。
内容域通过 `GET /api/v1/template-media/:slug/:file` 提供启用模板的已登记封面；此图片专用路径允许公开读取，不开放模板源码、配置或未登记文件。
图片 URL 附带内容版本，支持缓存验证；页面不访问上游图床，也不需要把 token 放进图片 URL。
训练目标不能把未经验证的支付链路、故障候选或完整实训验收写成已支持能力。
展示资料随模板打包，修改后需重新构建并重启 content-service、sandbox-service。首次接入图片端点还需更新 api-gateway 和 Helm 路由，以及用户端 web。

## Chart 运行时契约

模板自带的 Helm Chart 必须遵守以下约定，沙箱才能无参数装配：

1. **单 release、命名空间隔离**：Chart 必须能部署进沙箱专属命名空间，release 名等于模板 slug；
2. **镜像走 values 注入**：镜像地址必须可通过 `global.image.registry/repository/tag/pullPolicy/pullSecrets`
   及各服务 `image.*` 覆盖，Chart 内不写死镜像仓库；
3. **依赖地址可配**：数据库、缓存、消息及外部模拟服务地址必须由 values 提供，缺省值指向本沙箱内依赖；Loki/Prometheus 等平台观测服务通过受控地址接入；
4. **资源约束**：命名空间级配额由平台统一负责，Chart 声明容器 requests/limits，预算口径与清单 `resources` 一致；不得放宽平台上限。需要 LimitRange 时由平台统一管理；当前不将其视为已实现能力；
5. **可重复部署与卸载**：部署流程明确首次安装、重试及失败清理策略；`helm install` 本身不具有幂等性。卸载及沙箱销毁后不留运行数据残留，PVC、外部存储及模拟任务必须有回收策略；
6. **业务依赖与外部模拟**：数据库、缓存、消息及外部模拟服务的状态按沙箱隔离，不能默认共用生产业务依赖。平台观测服务可以共享，但证据按沙箱区分；
7. **评分边界**：`role` 描述服务类型，当前通用评分的限制不替代场景验收；中间件故障必须结合该场景的依赖健康与业务结果验证恢复。

## 扩展治理规则

模板规范通过三道机制保证向前兼容，**新增信息一律采用"加可选字段"方式，不破坏旧程序**：

1. **版本位**：`apiVersion` 显式声明。只有以下三种情况才允许出 `v2`——已有字段语义改变、
   可选字段变必填、枚举值重定义；纯粹新增字段永远停留在 v1；
2. **未知字段忽略**：解析器（yaml.v3 默认模式）不开启严格字段检查，旧版本程序读到含新字段的模板不会报错，新字段被忽略；
3. **核心外皆可选**：除 `apiVersion`/`slug`/`name`/`chart`/`services` 外全部可选，新增字段必须以缺省值安全运行。清单字段可选不代表正式模板可以省略准入验收。

可预见的扩展方向（均不需要 v2）：访问方式声明（端口/路径/账号）、架构图与说明文档、
适配故障引用、标签分类、最低资源/节点选择器要求、初始化数据来源等。
